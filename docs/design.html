1. 概要

gitteam は、チームの GitHub 標準を gitteam.yaml に記述し、CLI（typer）と Web UI（Streamlit）から GitHub とメンバーの PC に冪等に適用するツールである。 GitHub への接続と認証は gh CLI に委ね、自身は認証情報を保持しない。すべての変更操作は dry-run による事前確認を経て実行される。

設計の核は「純粋なコア（検証・計算・ペイロード生成）」と「副作用を持つ統合層（git / gh の実行）」の分離である。 ユースケース層はこの 2 つを組み合わせ、CLI と UI はユースケース層を共有する。これにより UI は CLI と同じ処理を同じ dry-run 基盤で実行できる。

2. 設計方針と決定事項

ID決定理由代替案と却下理由
D-1GitHub への接続は gh CLI に委ねるトークン管理・ブラウザ認証・ページネーションを gh が担い、gitteam は秘密情報を持たないPyGithub / Octokit 直接利用: トークン保管が必要になり、認証 UX も自作になる
D-2純粋コアと統合層の分離検証・ペイロード生成をネットワークなしで単体テストできる。UI と CLI で同一ロジックを共有コマンドごとに直接 subprocess: テスト困難、dry-run の一貫性が保てない
D-3dry-run は Runner で一元化（mutating=True の呼び出しを表示のみに置換）全コマンドが自動的に dry-run 対応になる。UI の「内容を確認する」もこの出力を解析するコマンドごとに if 分岐: 漏れが生じる
D-4ブランチ保護の既定エンジンは Rulesetsパターン指定可、ブランチ未作成でも設定可、GitHub が投資している APIclassic protection: 既存ブランチのみ、パターン不可。互換のため選択肢として残す
D-53 形態を mode + 自動判定 plan + 可視性から能力に写像する使えない機能を実行前に理由付きでスキップでき、途中失敗を避ける形態ごとの分岐をコマンド内に散在: 保守困難
D-6UI の設定編集は ruamel.yaml のラウンドトリップで行う生成した設定ファイルのコメント（説明）を保持できるPyYAML の dump: コメントが消え、初心者向けの説明が失われる
D-7作業ディレクトリで見つかった設定は明示的信頼まで使わない。例外は副作用のない ops branch check / ops commit check（git hooks から呼ばれる）で、未信頼設定の conventions のみを警告付きで読むクローンした他人のリポジトリ同梱の設定が git 設定や生成フックを変えるのを防ぐ（git の safe.directory と同じ考え方）。検査だけは、呼び出し元のフック自体がリポジトリ由来のコードであり信頼面が増えないため、クローン直後のコミットを止めない常に信頼: セキュリティレビューで High 相当の経路と判定。検査もブロック: gitteam を入れた人だけ全コミットが止まり、sh フォールバックと挙動が逆転（初期版で採用し撤回）
D-8UI は変更操作を「確認→実行」の 2 段階に統一し、実行は確認時と同一の引数で行う初心者の誤操作防止と、確認内容と実行内容の一致保証グローバル dry-run トグル: 状態が 2 か所に分かれ分かりにくい（初期版で採用し撤回）
D-9CLI メッセージは英語、UI は日本語CLI は git / gh の出力と混在するため英語で統一。UI は対象読者に合わせて日本語化し、dry-run 行を日本語の操作説明に変換するCLI も日本語化: 未決事項として保留（§13）

5. 主要フロー

5.1 repo init

dry-run 時、対象リポジトリが未作成で一覧系 API が 404 を返す場合は「空」とみなして計画を続行する（_list_or_empty）。これにより作成前でも実行計画を完全に表示できる。

5.2 UI の確認→実行

describe_command は dry-run 行（例 gh api repos/o/r/labels -X POST）をエンドポイントとメソッドで分類し、「o/r にラベルを作成」のような日本語に変換する。 Runner は dry-run 行を soft_wrap=True で折り返さずに出力するため、1 行 = 1 コマンドとして解析できる。

5.3 設定の探索と信頼

config_or_default()（ops / dev が使用）は設定が無ければ既定値にフォールバックするが、UntrustedConfigError は再送出する。未信頼の設定を黙って無視しないための設計である。

conventions_for_checks()（branch check / commit check が使用）は読み取り専用の例外で、未信頼設定でも conventions だけを返し、config trust を促す警告を 1 行出す。返した値の到達先は re と画面出力のみで、subprocess 引数・ファイル生成・git 設定には流れない（§10 S-4）。

5.4 能力判定

入力取得方法出力への影響
mode設定teams（org のみ）、org_rulesets / push_rulesets / required_workflows / internal_repos（enterprise のみ）
plan設定が auto なら gh api orgs/{owner} または gh api user の plan.name。読めなければ free と仮定し警告。AppContext がキャッシュ有料（pro / team / enterprise）なら private でも保護可
visibilityリポジトリの実値（存在時）または設定の既定public なら常に保護可

apply_protection は branch_protection が偽なら理由（notes）を警告として表示し「skipped」を返す。失敗ではなく設計上のスキップとして扱う。

既存ファイルは force=False の限り保持する。テンプレート内でシェル / GitHub Actions の $ は $$ と書き、${{ }} は Template の無効プレースホルダとしてそのまま残る。

git hooks の設計

  • commit-msg: gitteam が PATH にあれば gitteam ops commit check --message-file に委譲、無ければ POSIX sh の同等実装で検証。
  • pre-push: stdin の各 ref について、ブランチ名（保護ブランチは除外）と push 範囲のコミット件名を検証。新規ブランチは --not --remotes で範囲を決める。
  • フックに埋め込む値は §10 の文字集合検証を通ったものだけであり、単一引用符で囲んだ変数代入として展開される。
  • pre-push 内の gitteam 呼び出しは </dev/null で stdin を切り離し、git が渡す ref 一覧を子プロセスが消費しない。
  • commit check は # 行と scissors 行（git commit -v の diff）以降を無視する。クローン直後で gitteam.yaml が未信頼でも、検査は conventions だけを読んで動く（§5.3）。

GitHub Actions conventions.yml

PR の opened / edited / synchronize / reopened で、ブランチ名・PR タイトル・コミット件名を検証する。PR タイトルやブランチ名は env: 経由で渡し、run: 内に直接展開しない（式インジェクション対策）。

12. 拡張の手引き

新しいコマンドを追加する

  1. commands/<area>.py に fn(ctx: AppContext, ...) を実装する。外部呼び出しは ctx.gh / Git(ctx.runner) のみ。
  2. 変更系の呼び出しは必ず mutating=True（既定）で Runner を通す。これで --dry-run と UI の確認表示が自動的に機能する。
  3. cli.py に typer コマンドを登録する。
  4. UI に載せる場合は stage_action("key", fn, ...) と render_action("key") を置く。新しい gh エンドポイントは services._describe_api に日本語説明を追加する。
  5. 純粋ロジックは tests/ に単体テスト、UI は test_ui.py に描画テストを追加する。

設定項目を追加する

  1. config.py の該当 dataclass にフィールドと既定値を追加（_build が自動で受け付ける）。
  2. 生成フックやワークフローに埋め込む値なら _safety_problems に文字集合検証を追加する。
  3. templates/gitteam.example.yaml にコメント付きで追記し、必要なら UI のかんたん設定と save_simple_settings に反映する。

能力を追加する

Capabilities にフィールドを追加し resolve で算出、as_rows と glossary.CAPABILITY_INFO に説明を追加する。test_capability_info_covers_every_row が両者の整合を検証する。

13. リスクと未決事項

Mediumプラン（Organization / 個人）が読めない場合に free と仮定する
保護が「スキップ」されて意図しない状態になり得る。対策: どちらの形態でも警告を出し、plan: の明示指定を README と doctor で案内済み。
Mediumclassic 保護は既存ブランチにしか適用できない
新規リポジトリでは既定ブランチのプッシュ後にのみ有効。対策: 既定を Rulesets にし、classic 選択時は警告してスキップ。
LowGitHub API の仕様変更（Rulesets パラメータ等）
ペイロードは protection.py に集約されており、変更点は 1 か所で吸収できる。

  • CLI メッセージの日本語化（現状は UI の要約のみ日本語）
  • 作業ディレクトリの設定を信頼する際に、内容の差分やリスク項目を表示するか
  • Enterprise 向けの組織レベル Rulesets を適用するコマンドの追加
  • Streamlit のファイル監視が効かないケースの原因究明（開発体験）

B. 用語

dry-run
変更系コマンドを実行せず表示のみ行うモード。Runner.dry_run。
mutating
Runner.run の引数。真なら dry-run で抑止される。読み取りは偽で呼ぶ。
Capabilities
mode × plan × visibility から算出した機能可否。
信頼（trust）
作業ディレクトリ由来の設定を使用可と登録した状態。trusted-configs.txt。
ActionState
UI の確認→実行で保持する関数・引数・計画・結果。
Rulesets
GitHub のブランチ保護の新 API。パターン指定と冪等更新が可能。
